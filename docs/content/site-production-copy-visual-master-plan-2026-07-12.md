# CabLate 全站 Production、文案與視覺 Master Plan

這份文件把既有的站點目的與頁面角色，轉成可以長期執行的 production 規則。它不是一次性的改版清單，而是每次新增內容、調整版面或準備上線前，都要回來檢查的門檻。

## 1. 本輪結論

目前網站的品牌表面已經成立：紫色識別、暖白紙面、固定導覽、Noto Sans／Noto Serif 字體，以及桌機／手機的響應式骨架都能辨認為同一個 CabLate。接下來不應再推翻主視覺，而要做一次「敘事與資訊結構收斂」：

1. 每一頁只服務一個讀者決策，刪掉因為「手上有素材」而加入的旁支。
2. 文案先講讀者正在遇到的情況，再介紹方法名稱、產品或工具。
3. 同一個「不是 A，而是 B／先……再……／真正……」句型不能變成全站模板；保留必要的判斷，但改成直接、具體、可朗讀的句子。
4. 紙張是表面語言，不是把每一段都包成同款卡片的理由。卡片、迴紋針、標籤與英文索引只能協助分組、定位或建立敘事。
5. 任何數字、案例、訂閱承諾、合作限制與外部連結，都要在它支撐的主張旁邊，並保留日期、來源與授權狀態。
6. 文案 source 在作者確認前不直接修改；先以完整編號清單確認，確認後才套用選定項目。

## 2. Scope 與不可碰範圍

### 本輪處理

- `/`
- `/about/`
- `/expertise/`
- `/work/`
- `/courses/`
- `/services/`
- `/articles/`
- `/articles/category/[category]/`
- `/articles/tag/[tag]/`
- `/articles/tags/`
- `/404/`
- 共用導覽、Footer、紙面容器、文章索引元件與 SEO／表單 production gate

### 本輪暫不處理

- `/starter-pack/`：使用者已要求移除；正式網站不再提供此路由，相關頁面與專屬素材已清理。
- `/articles/[slug]/`：文章內頁保留既有內容，另開文章編輯輪次。
- `/courses/[slug]/`：課程內容頁保留既有內容，另開產品頁編輯輪次。
- `/search/`：先不重新規劃視覺與文案。
- `/privacy/`：保留法律文件專用排版與必要責任措辭；只做合法性、日期與實際追蹤狀態核對，不套用 Human Speaker 改稿。

## 3. Production 目標與 release gate

### 3.1 對外目標

陌生訪客在五秒內知道：CabLate 能協助他把 AI 使用上的失控、重做與交付問題拆開來看，並且能選擇文章、學習、作品或合作其中一條合理路徑。理想情緒順序是：

```text
被說中 → 鬆一口氣 → 看見新的問題解釋 → 相信問題可以拆解
→ 看見公開證據 → 採取一個小而明確的下一步
```

### 3.2 上線前必過

- `npm.cmd run check`：0 errors、0 warnings。
- `npm.cmd run validate:content`：所有公開課程內容通過。
- `npm.cmd run build`：預期 route inventory 與頁數一致，且沒有未解決的正式資產 URL。
- `git diff --check`：無 whitespace error；不得誤觸使用者既有 dirty worktree。
- 桌機至少 1440×900、手機至少 390×844 實際瀏覽；`scrollWidth === clientWidth`，標題、CTA、表單與紙張內距均不溢出。
- 鍵盤可完成 skip link、導覽、手機選單、所有 CTA、表單與 carousel；`:focus-visible` 清楚可見。
- `prefers-reduced-motion` 下不依賴動畫才能讀懂內容；View Transition／Reveal 失效時內容仍直接可見。
- 每一頁只有一個 Primary CTA 意圖；次要連結不能在同一屏競爭相同決策。
- 所有動態數字、作品證據與合作紀錄都有 `asOf`、公開範圍與授權狀態。

## 5. 文案治理規則

### 5.1 Human Speaker 流程

本站對外文案採用 `general/.agents/skills/speak-human-tw` 的雙重確認流程：

1. 先鎖定價格、數字、專有名詞、網址、真實姓名／引言與承諾條款。
2. 逐頁列出每一處建議修改：檔案與行號、原句、問題、具體改法。
3. 明確詢問作者哪些項目要改；未收到確認前，不改 source。
4. 只套用作者勾選的項目，完成後做保真回讀與台灣用語檢查。

### 5.2 全站語感

- 先寫讀者看見的場景，再寫方法名稱：先說「AI 忘記前文」，再說 Context。
- 一句只承擔一個主要意思；把抽象名詞還原成「誰做什麼、在哪裡卡住」。
- 「不是 A，而是 B」全站只保留必要的核心定義，其餘改用並列、情境或時間對比。
- 刪掉「好消息是、真正的問題在於、這意味著、總的來說」等導引或空泛收尾；沒有新事實就不補新金句。
- 不用「旗艦、完整、全面、真正、無縫、令人期待」替代證據；寫不出具體內容就刪掉。
- 技術名詞第一次出現時加一句白話定義；後續可用簡稱，不要每段重新解釋。
- 中文全形標點與台灣用語；價格、日期、數據與引用原話一字不漂。
- 標題先以可朗讀的自然句寫成，再用 `text-wrap: balance` 輔助；不能靠 `<br>` 大量硬切來掩蓋句子問題。

### 5.3 素材閘門

每個新段落或視覺元素先回答：

1. 它支援哪一個主張或讀者決定？
2. 它放在這一頁，是否比主要歸屬頁更有用？
3. 拿掉它後，訪客少知道哪個事實、少了哪個信任理由？
4. 它是主張、解釋、故事、證據還是裝飾？
5. 是否有來源、日期、授權與可維護的 HTML/CSS fallback？

## 6. 本輪已發現的視覺與資訊架構冗餘

### P0／P1：先收斂

1. `paper-card`、`page-paper`、`.paper-page > .page-paper` 三層容器同時管理背景、padding、陰影與 `!important`，容易讓首頁與內頁出現不同內距或背景裁切。下一輪建立明確的「表面／版面／內容內距」三層 contract，讓頁面只選 modifier。
2. About、Expertise、Work、Courses、Services、Articles 的 Hero 都使用「小標＋英文索引＋大標＋段落」的近似節奏。保留同一品牌表面，但每頁至少改變兩項：資訊位置、首屏密度、視覺錨點或入口形式。
3. 迴紋針與 `paper-label` 幾乎出現在每個長頁區塊；它們失去「這是一份可獨立移動的檔案」的語意。原則改為每頁最多一個主要夾子／標籤，只有在分組或指示閱讀起點時使用。
4. 桌機 rail 與 mobile menu 重複同一套中文／英文導覽；Footer 又完整重複主要導覽。保留 Footer 作為頁尾尋路，但將 rail 的英文副標改為少量、真正有用途的索引，不再每個入口都堆一個英文名。
5. 手機 `.paper-card` 已移除陰影，但 mobile menu 的 `summary` 與展開 `nav` 仍自行使用 filter shadow；需統一紙張邊緣規則，避免選單看起來像另一層深色底。
6. Courses 已改以免費文章與問題診斷作為低門檻入口；需持續檢查已退役產品的舊連結是否回流。

### P2：清理重複與死碼

1. `src/components/sections/LatestArticles.astro` 仍保留「推薦閱讀」整段，但目前沒有 production 頁面引用；刪除前先確認它不再是首頁預備入口，避免停更文章被誤呈現為最新內容。
2. `authority.ts` 的 `publicProofs`、`visitorPaths`、`beliefs`、`expertiseAreas` 沒有被主要頁面使用；Home 又自行維護 `visitorRoutes`。下一輪要決定單一 source of truth，刪除未使用副本或真正接回對應頁面。
3. `global.css` 仍保留 legacy aliases 與未進入 redesign slice 的元件樣式。先做使用狀態盤點，再按頁面邊界刪除；不可為了「看起來乾淨」直接整批移除。
4. Archive category、tag、tags 三頁共用同一套 Hero、空狀態與回程導覽；保留共用元件，但依頁面任務只留下必要的索引資訊與一個情境回程連結。

## 7. Production 風險與處理順序

### P0：正式上線前一定要處理

- GA4 在 `BaseLayout.astro` 全站直接載入，現有 Privacy 頁沒有同意管理或拒絕前置流程。確認台灣適用的隱私／Cookie 政策、是否需要 consent gate，並讓文件的更新日期與實際追蹤行為一致。
- Kit 外部表單 script、success/error state、無 JavaScript fallback、垃圾信防護與取消訂閱流程要在實際 production 帳號驗證；目前 `recaptcha` 設定為 false，需確認是否為有意決定。
- Build 的 8 個 `__VITE_PUBLIC_ASSET__…` 警告要追到來源；production HTML 不得留下無法解析的 asset placeholder。

### P1：下一輪一併修

- 將 JSON-LD script 明確加上 `is:inline`，消除 Astro hints；整理 deprecated `ViewTransitions`、`document.execCommand`、Lucide `Github`／`BarChart3`。
- `CourseLayout` 的 `headings` 未使用，確認是否要移除 props 或真的渲染課程目錄。
- 建立 route/link smoke test：主要入口、`cabai.cablate.com`、GitHub、npm、Threads、RSS 與 privacy link 都要回應正確，並確認已退役的 `/starter-pack/` 不再出現站內連結。
- 檢查圖片 `width`／`height`、`loading`／`fetchpriority` 與紙張背景資產的載入量，避免 carousel、OG 圖與 paper texture 造成 CLS 或不必要下載。
- 檢查 heading hierarchy、SEO title／description、aria label 與可見文字是否一致；英文 decorative label 不得成為螢幕閱讀器唯一資訊。

### P2：持續品質

- 將每頁桌機／手機截圖與 QA 結果記錄在 `docs/design/references/current-pages/`，只保留可追溯的基準檔。
- 每次文案改動後重跑 mobile heading break、scroll offset、focus-visible、carousel dots 與 mobile menu 內縮檢查。
- 以真實訪客任務做五秒／三十秒 review，而不是只看 CSS 是否「漂亮」。

## 8. 分階段執行方案

### Phase 0｜基線與狀態鎖定

- 清理已退役的 Starter Pack route、專屬元件與設計輸出；保留其他使用者既有 dirty worktree。
- 建立本 master-plan，記錄 route inventory、production 基線與現有視覺 contract。
- 確認 Courses 哪些入口真的可取得；未確認前，不新增任何產品 CTA。

### Phase 1｜文案核准

- 依本文件第 9 節的 audit 清單逐條確認。
- 作者確認後才修改 Home、About、Expertise、Work、Courses、Services、Articles 與 archive 文案。
- 完成保護清單回讀：數字、日期、專名、連結、引用與承諾條款不得漂移。

### Phase 2｜共用視覺 contract

- 把 paper surface、layout shell、content inset、clip、label、shadow 拆成可驗證的共用層。
- 讓每頁保留自己的視覺語法：About 是時間軸、Expertise 是診斷表、Work 是案例檔案、Courses 是路線圖、Services 是合作 brief、Articles 是編輯索引。
- 同一頁只留一個主要裝飾錨點；影像與 imagegen 只作提案或氛圍，不承擔必要文案與證據。

### Phase 3｜Production hardening

- 修正 asset placeholder、GA4 consent、Kit fallback／spam protection、JSON-LD hints 與 deprecated API。
- 建立 route/link、accessibility、performance、responsive 的自動化 smoke checks。
- 以 desktop／mobile 截圖逐頁 review，確認 header offset、紙張內距與 title wrapping。

### Phase 4｜觀測與節奏

- 只追蹤能回答決策的事件：primary CTA click、文章起讀、合作情境送出、訂閱確認；不為了「有數據」塞滿事件。
- 每季回顧一次：哪些頁仍讓訪客不知道下一步、哪些素材已過期、哪些 proof 缺日期或授權。
- 若商業狀態或產品開放狀態改變，先更新本文件與 `site-purpose-page-role-and-cta-master-plan-2026-07-12.md`，再改 source。

## 9. 本輪文案 audit 清單（source 尚未修改）

以下清單是依 `speak-human-tw` 的第一輪規則整理；每一項都保留原始位置、問題與具體建議。使用者已於 2026-07-12 確認全部 62 項，並已套用至 source；保留此清單作為改稿前後的可追溯對照。

1. `src/pages/index.astro:70` — 原句：「讓 AI 做完，也讓成果真的能用。」問題：口號式對稱，「能用」沒有說清楚成果要達到什麼狀態。建議：「讓 AI 把工作做完，成果也能放心交付。」
2. `src/pages/index.astro:71` — 原句：「如果你已經在用 AI，卻還是經常重做、走偏，或不敢直接採用成果，問題通常不只在 Prompt。任務怎麼拆、資料怎麼給、工具怎麼接、做到哪裡算完成，才是成果能不能穩定的關鍵。」問題：否定平行結構與抽象列舉疊在一起，讀者還沒看見自己的場景就先遇到術語。建議：「你已經在用 AI，卻還是常常重做、走偏，或不敢直接交付。很多時候不是模型或 Prompt 不夠好，而是任務、資料、工具和完成標準沒有接起來。」
3. `src/pages/index.astro:72` — 原句：「先看看問題卡在哪」問題：CTA 偏口語但目的地不夠明確。建議：「找出問題卡在哪一層」
4. `src/pages/index.astro:84` — 原句：「真正需要的，不是每次得到一個漂亮答案，而是換任務、換工具或換人後，成果仍能被重現、檢查和修正。」問題：又一次使用「真正／不是 A 而是 B」，可改成直接定義可靠流程。建議：「可靠流程要能在換任務、工具或交接對象後，仍讓成果被重現、檢查與修正。」
5. `src/pages/index.astro:85` — 原句：「好消息是，這些問題都能拆開檢查。你不必一次換掉整套工具，只要先找出最容易失效的那一層。」問題：通用積極開場與「你不必」式安撫沒有新增資訊。建議：「這三種失效都可以逐層檢查。先找出最容易出錯的一層，不用先換掉整套工具。」
