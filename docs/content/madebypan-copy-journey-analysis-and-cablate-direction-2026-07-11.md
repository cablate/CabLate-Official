# madebypan 全站文案分析與 CabLate 文案方向

## 0. 這份文件要解決什麼

這次不是研究 madebypan 放了哪些區塊，也不是要把它的句子換成 CabLate 的名詞。

真正要回答的是：

1. 訪客進入每一頁時，腦中原本在想什麼？
2. 頁面用了什麼順序，改變訪客的理解、情緒與行動？
3. 哪些做法值得借鑑，哪些做法看似豐富、實際上會削弱信任？
4. CabLate 要怎麼使用 Content OS，讓素材服務訪客決策，而不是讓訪客替我們消化素材？

這份文件先作為內容策略與文案打磨的基準。確認方向後，再逐頁改寫網站。

## 2. madebypan 全站真正有效的訊息架構

madebypan 最強的地方，不是文筆華麗，而是常能在很短的篇幅內完成三件事：

1. **替訪客說出現在的處境**：興趣很多、不知道如何開始、已經用了 AI 但產出不能用、看了很多內容仍卡在自己的問題。
2. **提供一個容易記住的新解釋**：不是再學更多工具，而是成為「AI 指揮家」；不是學寫程式，而是用自然語言把想法做出來；不是 Claude Code 只能寫程式，而是 Agent 可以替你完成流程。
3. **給一個低理解成本的下一步**：看指南、選工作坊、預約諮詢、加入企業方案。

它常用的心理順序是：

```text
你是不是也這樣？
→ 問題不是你不夠努力
→ 是你用錯理解方式
→ 原來可以換一種做法
→ 我有一條具體路線
→ 你可以從這裡開始
```

這套順序會讓訪客先感到「被理解」，再願意聽方法。方法名稱是解釋，不是開場考題。

## 4. madebypan 值得借的，不是句子，而是四種能力

### 4.1 用讀者語言說出「卡住的那一刻」

好的句子不是「我專精 Agent、MCP、Skill」，而是：

> 你已經會叫 AI 幫忙，但每次都要重新解釋、重新修正，最後還是不敢直接交付。

讀者先認出自己的生活，才有興趣知道問題叫 Context、Harness 還是驗收設計。

### 4.2 給一個能重述的新解釋

「AI 指揮家」「從一問一答到讓 AI 動手做完」都容易被訪客記住並轉述。CabLate 也需要一個比術語更早出現的解釋：

> 問題通常不是 AI 不夠強，而是它不知道現在要完成什麼、可以用哪些資料、做到什麼才算完成。

這句話可以自然帶出 Cab 的工程判斷，但不要求訪客先學名詞。

### 4.3 讓產品代表一段進展，不是一包內容

madebypan 有效的產品開場多半先講「做出網站」「把想法變成工具」「讓 AI 動手完成流程」，而不是先列課綱。CabLate 的課程也應先回答：上完後，訪客的工作方式有什麼實際改變？

### 4.4 每頁有明確下一步

即使 madebypan 後段經常過長，它的入口通常很明確。CabLate 應保留這種清楚，但讓 CTA 建立在適配，而不是焦慮或誇張的效率承諾上。

## 5. madebypan 不該借的四件事

### 5.1 不用高倍數承諾代替證據

「十倍甚至百倍」「每天省三小時」「產能提升三倍」會快速拉高期待，也會讓專業訪客開始找漏洞。CabLate 的優勢是工程可信度，應說明 baseline、限制、驗收與日期，不該加入同類型口號。

### 5.2 不把銷售頁寫成所有疑慮的總和

每多一個案例、贈品、課綱與比較表，不一定多一分信任。當訪客已經理解結果、適配與證據，繼續加內容反而會製造「是不是需要這麼多解釋才賣得動」的感受。

### 5.3 不用作品數量取代判斷過程

Portfolio 最明顯的問題是：作品很多，但訪客很難知道哪一件最能證明自己在意的能力。CabLate 的 Work 頁應選少數案例，說清楚問題、關鍵判斷、限制與結果。

### 5.4 不把重要文字做成圖片

圖片適合視覺節奏與證據，不適合承擔唯一的銷售文案。可見文字、可索引 HTML、圖片 alt 與視覺素材應各司其職。

## 6. CabLate 現況：前一版與下一版的差別

### 6.1 現在的版本已經比「素材全倒上去」好，但主角仍常是 Cab

目前網站已經有幾個正確改變：

- 不再把首頁做成完整履歷。
- Courses 開始用「離成果多遠」分流，不只列商品。
- Services 有適合、不適合、交付與責任邊界。
- Work 明確區分 Case Study 與 Project Note。
- 文案避免未授權客戶名、營收與永久化的動態數字。

問題在於，內容順序仍經常從 Cab 的知識結構出發：

```text
我是誰
→ 我相信什麼
→ 我有哪些方法
→ 我有哪些作品
→ 我有哪些課程／服務
```

訪客真正需要的是：

```text
你說中了我的處境
→ 原來問題可以這樣理解
→ 我現在少了一個什麼環節
→ 你為什麼有資格幫我
→ 我最適合從哪一步開始
```

### 6.2 具體前後對照

| 區域 | 目前版本 | 訪客可能的感受 | 下一版方向 |
|---|---|---|---|
| Home Hero | 「嗨，我是 CabLate」＋能力描述 | 知道名字，但還不知道為什麼要留下 | 先命中「AI 做得快，卻做不穩、做不完」的處境，再介紹 Cab |
| Home routes | 想學習／想合作／想看作品 | 分流清楚，但仍是網站分類 | 改成訪客意圖：「想先把 AI 用對」「想完成一個作品」「想改善團隊流程」 |
| 核心主張 | 判斷力比執行力值錢 | 有立場，但較抽象 | 保留為世界觀，在讀者先認出問題後出現 |
| 三個方法 | Harness、Context、Skill | 專業，但像要先學 Cab 的分類 | 先用三個常見失效情境，方法名作第二層解釋 |
| Featured Project | 深度工程手冊 | 可信，但太快進入單一產品 | 先證明「這套判斷來自實作」，再依訪客路徑放對應 proof |
| About | 旅程、六個領域、開源、四原則 | 完整但像整理好的履歷 | 用 2–3 個轉折證明「為什麼 Cab 特別在意做對、交付與驗收」 |
| Courses | 四段學習路線，後面多數未開放 | 理解路線後卻無法前進，產生落差 | 只呈現現在真的能做的下一步，未開放產品不要占主敘事 |
| Services | 一開場就談條件、風險與邊界 | 專業安全，但尚未期待成果就先被審核 | 先描述完成後的改善，再用邊界建立安全感 |
| Articles | 六個研究主題＋文章清單 | 知道 Cab 很廣，但不一定知道先讀什麼 | 依真實問題提供 3–5 個推薦起點與閱讀路徑 |

## 7. CabLate 全站應共用的情緒主線

CabLate 不需要靠 FOMO 或誇張倍數推動。更適合的情緒路徑是：

```text
被理解
→ 鬆一口氣
→ 看見新解釋
→ 產生「我也做得到」的希望
→ 用真實證據建立信任
→ 願意採取一個小而明確的行動
```

每一段文案完成後，都要檢查：

1. 訪客現在多相信了什麼？
2. 訪客現在少擔心了什麼？
3. 訪客現在更願意做哪一步？

如果三題都答不出來，這段多半只是資訊，不是有效文案。

## 8. Content OS 的正確用法：從倉庫改成證據調度系統

Content OS 已經有 A–H 的定位、作品、知識、產品、證明、故事與延伸資產。問題不是素材不足，而是缺少「什麼時候不該用」的選擇規則。

### 8.1 素材調用閘門

任何素材進頁面前，必須依序通過五個問題：

1. **這一頁只負責哪一個決策？**
2. **訪客在這個位置正擔心什麼？**
3. **這個素材能改變哪個信念或降低哪個風險？**
4. **它是主張、解釋、故事還是證據？同一角色是否已經有更強素材？**
5. **讀完後要把訪客帶去哪一步？**

只要第 2、3 題答不出來，素材就不應出現在這一頁。

### 8.2 A–H 不等於八個網站區塊

| Content OS | 應扮演的角色 | 不該做的事 |
|---|---|---|
| A 定位 | 提供一句主張、身份與說話角度 | 把四種定位一次放進 Hero |
| B 作品 | 為特定能力提供可檢查證據 | 把 repo 與專案全部列出 |
| C 知識 | 回答訪客正在問的問題 | 把方法論名稱當首頁導覽課綱 |
| D 產品 | 讓訪客選擇現在需要的進展 | 把未開放產品做成期待清單 |
| E 證明 | 在疑慮出現的位置降低不確定性 | 集中成與上下文無關的數字牆 |
| F 故事 | 解釋 Cab 為什麼形成這種判斷 | 把 About 寫成英雄旅程或私密自白 |
| G 主題 | 建立問題導向的閱讀路徑 | 一次公開所有內容分類 |
| H 延伸資產 | 提供驗證、持續關係與外部入口 | 因為「我們有」就塞進首頁 |

### 8.3 CabAI、互動簡報與各種工具的定位

它們不是首頁必備名詞，也不是每頁都要露出的品牌資產。它們只有在能完成下列工作時才出現：

- CabAI：證明 Cab 能把知識產品做成交付系統，或作為某個產品的實際入口。
- 互動簡報／Interactive Engine：證明 Cab 對教學體驗與現場互動有實作能力。
- GitHub／npm：證明技術不是口頭主張。
- 多 Agent 內容系統：證明 Cab 如何把一人事業的資訊與交接問題系統化。

如果一頁正在回答別的問題，這些名稱就不應硬出現。

| Articles | 我有一個具體問題，先讀什麼？ | 好奇 → 很快得到答案 → 發現有更完整脈絡 | 推薦起點、系列、更新日、來源 | 讀旗艦內容／訂閱 |
| Courses | 我需要學到什麼程度？ | 焦慮 → 被允許從小步開始 → 找到適合產品 | 目前可交付狀態、適合／不適合、學完的進展 | 取得一個可用產品 |
| Services | 團隊／專案卡住，不知道該買課還是找人 | 被理解 → 看見理想成果 → 知道合作方式 → 對邊界安心 | 匿名案例、交付物、責任與限制 | 提交合作情境 |
| Starter Pack（已退役） | 我想開始，但不想先買錯 | 鬆一口氣 → 完成小成果 → 願意保持聯絡 | 具體交付內容與下一步 | 不再提供公開入口 |

## 10. CabLate 首頁的新版敘事骨架

首頁不應再從「Cab 擁有什麼」展開，而應從「訪客正在經歷什麼」展開。

### 10.1 建議順序

1. **問題型 Hero**：說出 AI 做得快、卻做不穩、做不完的落差。
2. **新解釋**：問題常在任務、資料、工具、驗收與責任沒有接好，不只是模型不夠強。
3. **三種訪客意圖**：先把 AI 用對／完成一個可交付作品／改善團隊流程。
4. **局部證據**：每條路徑旁只放能降低該疑慮的一項證據。
5. **Cab 的角色**：工程師出身，能把複雜技術拆成人能理解、AI 能執行、成果能檢查的流程。
6. **一個代表故事或案例**：不是先推產品，而是證明這套方法來自實作。
7. **推薦閱讀**：用一篇內容讓尚未準備購買的人先獲得價值。
8. **訂閱**：說清楚會持續收到什麼。

### 10.2 首屏文案候選

#### 版本 A｜最貼近目前主張

**H1**

> 讓 AI 不只做得快，也把事情做對、做完、做得能繼續用。

**副文案**

> 我是 CabLate，全端工程師出身的 AI 應用創作者與講師。我幫助已經在用 AI、卻常卡在失控、鬼打牆或無法交付的人，看清問題、拆好流程，讓成果可以被檢查，也能在下一次繼續累積。

**Primary CTA**：看看你現在卡在哪一步  
**Secondary CTA**：先讀一篇實作指南

#### 版本 B｜問題命中更強

**H1**

> AI 明明做得很快，為什麼最後還是要你一直重來？

**副文案**

> 很多時候，問題不是模型不夠強，而是任務、資料、工具與完成標準沒有接好。我把工程現場的拆解與驗收方法，整理成個人和團隊都能使用的 AI 工作流程。

**Primary CTA**：找出問題卡在哪一層  
**Secondary CTA**：認識 CabLate

#### 版本 C｜較適合陌生受眾

**H1**

> 把複雜的 AI 技術，變成你真的用得起來的工作方法。

**副文案**

> 從個人工作、產品實作到團隊導入，我不只教工具怎麼按，也會說清楚問題怎麼拆、資料怎麼準備、成果怎麼驗收，以及什麼時候根本不需要 Agent。

**Primary CTA**：選擇你的起點  
**Secondary CTA**：查看代表作品

### 10.3 建議採用方向

首選版本 A。它保留「判斷力比執行力值錢」的精神，但先把精神翻成訪客可感受的結果。核心主張可放在 Hero 後的「新解釋」區，而不是跟自我介紹競爭第一句。

## 11. 其他頁面的首版文案方向

### 11.1 About

**頁面承諾**：不是完整履歷，而是回答「為什麼 Cab 特別在意做對、交付與驗收」。

**H1 候選**

> 我不是一路都知道答案。只是做過夠多次，知道哪裡最容易出錯。

**敘事轉折**

1. 非本科轉職：體會「聽懂名詞」和「真的做得出來」差很多。
2. 從功能到系統：發現寫出來只是開始，權限、資料、部署與復原才決定能不能交付。
3. 從自己做，到幫別人做完：把經驗整理成教學、手冊、Skill 與合作流程。

只選能服務上述三個轉折的作品。六大專業領域不需要再次完整列出。

### 11.2 Expertise

**頁面承諾**：幫訪客辨識「AI 為什麼會卡住」，不是展示六項專長。

**H1 候選**

> AI 一直鬼打牆時，問題通常不只在 Prompt。

先用三個可辨識情境分流：

- 它不知道現在有哪些資料可以用。
- 它做了很多事，卻沒有明確完成標準。
- 每次都要重新教，好的做法沒有被留下來。

再分別帶出 Context Engineering、Harness Engineering 與 Skill 設計。

### 11.3 Work

**頁面承諾**：讓訪客看到 Cab 如何判斷，而不只是看產量。

**H1 候選**

> 我做過什麼不夠重要。更重要的是，遇到限制時我怎麼選。

每個項目只回答五件事：問題、限制、Cab 的角色、關鍵判斷、可公開結果。GitHub stars 放在對應作品旁，不另做大型聲量牆。

### 11.4 Articles

**頁面承諾**：讓有問題的人在 30 秒內找到推薦起點。

**H1 候選**

> 先找到你卡住的問題，再決定要學哪個名詞。

推薦入口先依問題，而不是依 Cab 的知識分類：

- AI 一直忘記前文或讀錯資料。
- Agent 做很多事，但結果不能用。
- 想把一次成功的方法留下來重複使用。
- 想把 AI 寫出的作品真的部署、收款與交付。

### 11.5 Courses

**頁面承諾**：幫訪客買得剛好，不是證明 Cab 有完整產品階梯。

**H1 候選**

> 不用先買最完整的課。先跨過你現在最卡的那一步。

只顯示現在能取得的內容。每個產品卡先寫「它幫你跨過哪一步」，再寫形式、內容與價格。未開放產品留在內部產品策略，不占訪客注意力。

### 11.6 Services

**頁面承諾**：先讓訪客看見完成後的改變，再談合作邊界。

**H1 候選**

> 把團隊現在最耗時間、最常重做的工作，整理成一條能使用、能檢查的 AI 流程。

建議順序：

1. 你可能正在經歷的情境。
2. 合作後希望改善的工作狀態。
3. 三種合作結果。
4. 對應證據。
5. 流程與交付。
6. 適合／不適合與責任邊界。
7. 提交合作情境。

邊界仍然保留，但不再比成果更早出現。

## 12. 文案驗收清單

每一頁進入實作前，必須能回答：

- [ ] 首屏是否先講訪客，而不是先列 Cab 的身份與名詞？
- [ ] 訪客能否在五秒內知道這頁與自己有何關係？
- [ ] 是否只有一個主要心理任務與一個 Primary CTA？
- [ ] 每一個方法名稱前，是否先出現人能辨識的問題？
- [ ] 每一個 proof 是否放在它要支撐的主張旁？
- [ ] 每一個故事是否只服務一個信念轉變？
- [ ] 拿掉 CabAI、Interactive Engine、repo 或某個產品名後，敘事是否仍成立？
- [ ] 是否有因為「我們有這份素材」而硬加的段落？
- [ ] 是否使用了沒有 baseline、期間或來源的效率承諾？
- [ ] 訪客讀完後，是否更清楚自己下一步，而不是只更了解 Cab？
- [ ] 文字是否專業、自然、白話，沒有 AI 常見的抽象堆疊？
- [ ] 動態數字是否有日期，案例與引言是否有公開授權？

## 13. 建議接下來的工作順序

1. 先確認首頁首屏方向，建議以版本 A 為基礎打磨。
2. 依情緒主線完成首頁全文，不急著把所有 proof、方法與作品補滿。
3. 用同一套「進站想法 → 情緒變化 → 必要證據 → CTA」重寫 About、Expertise、Work、Articles、Courses、Services。
4. 每頁寫完後，回到 Content OS 做素材選擇；不是先開素材庫找能塞的東西。
5. 文案確認後再改網站，逐頁用桌機與手機實際閱讀，檢查語句節奏、資訊量與 CTA 是否自然。

本輪先停在策略與首版文案方向，尚未修改目前網站頁面內容。
