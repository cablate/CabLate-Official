這個月 token 額度燒得特別快。

我有注意到，但一直說服自己是因為最近做的事情比較多。直到上週開始認真懷疑，仔細回想又沒多做甚麼事情，才決定認真查這件事。

這是我在 2026 年 3 月寫下的經過。當時最不對勁的地方，是編輯檔案之後，就算只送一句簡單請求，也會吃掉 2–3% 的五小時額度。

後來我在 Claude Code v2.1.71 的逆向裡，找到檔案 diff 重複進入請求的線索。它讓我開始查**畫面上那一句話以外，執行環境還送了哪些東西**。

> 本文保留 v2.1.71 的歷史觀察。2026-10-29 未重新驗證該版本程式，也未確認現行 Claude Code 是否仍有相同行為；2–3% 是我當時的訂閱額度觀察，不能套用為所有人的消耗率。

## 我怎麼察覺請求裡多了內容？

**先比較出問題前後，再把模型回述當成追查線索。**

當時我請 Claude Code 回述它收到的 system-reminder，幾次觀察下來，看到修改檔案的 diff，以及 Skill、Plugin 等相關資訊。其中有些模板還寫著不要主動向使用者提起。

這很容易讓人火大。畫面上沒聊多少，背後卻可能處理了大段內容，我原本根本沒有把它算進去。

不過，模型回述不等於原始請求封包。它可能漏掉或轉述內容，也不能靠它證明每一類資訊都在每輪注入。JSONL 對話紀錄同樣未必完整保存執行時組裝的所有輸入，翻不到不能證明當時沒送。

兩次操作呈現了比較有用的規律。

| 當時操作 | 我的觀察 |
|---|---|
| 編輯過檔案，再送訊息 | 看見檔案 diff 注入 |
| 補做一次 Read，再送訊息 | 那次沒再看見相同 diff |

這還不能證明全部成本來自 diff，但足以讓我懷疑，系統內部追蹤檔案的狀態出了問題。於是我開始逆向 v2.1.71。

## readFileState 在追蹤甚麼？

**它記錄執行環境認得的檔案內容，讓系統知道磁碟上的檔案後來有沒有改。**

當時逆向看到的流程，是拿記錄裡的檔案去比較修改時間，必要時重讀、比對內容，再把變動提供給模型。這本身有用途：如果人或其他程式在外面改了檔案，AI 下一步要知道。

問題出在狀態能不能正確更新。

resume 時，部分檔案追蹤狀態會從 JSONL 重建；這份資料與持續運作中的記憶體狀態未必相同。原先的逆向也懷疑路徑字串對不起來，會讓某筆狀態無法更新。

「路徑對不起來」是當時追查的解釋，本篇沒有保留足以逐步重現它的完整案例，所以不能把它直接判成所有額度異常的單一根因。可以保留的發現是，**重複 diff 值得沿檔案追蹤與 resume 狀態往下查**。

## 那每次 Edit 後都 Read，可以省嗎？

**當時補讀有緩解觀察，今天不適合把它設成每次必做。**

Read 本身會把檔案內容帶進上下文。檔案很大時，每改一次就完整重讀，也可能增加消耗。工具版本與狀態更新機制變了以後，這筆額外讀取未必還有原來的用途。

如果你現在懷疑相同問題，可以先用一個小檔案，在同一個 session 留下修改後幾輪的用量，再補讀一次，比較後面是否恢復。只有結果支持這個方向，才值得繼續追。

同樣地，也別只為了省額度就把對話關掉重開。新對話可能少帶歷史，卻會失去原本需要的脈絡；resume 也可能因為快取過期或輸入變動而重新處理大量內容。要比較的是完成同一件工作的總消耗。

## SDK 用戶也只能一直補 Read 嗎？

**要先看你的程式怎麼維持多輪對話。**

我當時的 SDK 程式每則訊息重新呼叫 `query()` 並 resume，因此每輪又走到狀態重建。CLI 裡觀察到的緩解方式，搬過去未必成立。

後來我先試著改 JSONL，擋住部分 diff 注入，仍沒有量到期待的快取改善；再換當時的 V2 常駐 session，數字才出現明顯變化。這段失敗很能說明，找到一個異常機制，還不等於找到了全部成本。

2026-10-29 查閱 [官方 SDK 文件](https://code.claude.com/docs/en/agent-sdk/typescript-v2-preview)，V2 已在 0.3.142 移除；官方建議 `query()` 的串流輸入或 `options.resume`。所以原文的「SDK 無解」早已不適合留作現況判斷。

## 遇到額度突然變重，先留下哪幾個證據？

**留下版本、前後操作，以及連續幾輪的實際用量。**

可以從這三項開始：

1. 記下 CLI／SDK 版本、模型和對話長度，標出剛才是否修改檔案、resume、切換工具或長時間閒置。
2. 有明細就記錄普通輸入、建立快取、讀取快取和輸出；只有訂閱百分比，就記百分比，別把它換算成 API 費用。
3. 一次只改一個條件，再看後續幾輪是否下降。別讓「剛好變好了」直接變成根因證明。

我最初那個「是不是自己做太多」的懷疑，並沒有因為逆向而變得比較不合理。只是後來多了證據，讓我可以把使用量、系統附加內容和快取分開看。
