你叫 AI 做一個網站，它很快產出頁面，看起來也能打開。接著你才發現首頁塞了用不到的功能、配色不一致，或是文章頁缺少該有的搜尋資訊。畫面出來之後，還有一連串決定和檢查要做。

我在 2026 年初用 Claude Code 建 CabLate 官網時，先決定網站的用途和結構，再讓 AI 按區塊實作。後來要把深色遊戲風改成淺色主題，那次改版讓我更清楚看到：規格清楚的重複修改適合交給 AI，方向和驗收仍要有人負責。這是當時的建站紀錄，工具與框架的功能今天可能已經不同。

## 開始寫之前，要先決定甚麼？

**先說清楚網站要放甚麼，以及如何部署。** 當時我的需求是放文章與作品集、優先產生靜態頁面、能使用元件，並部署到 Cloudflare Pages。我選了 Astro，因為它符合這些需求。框架選擇要跟專案條件一起看，不能只靠一張新舊版本混在一起的比較表決定。

接著我決定專案結構：文章放在 `src/content/articles/`，版面放在 `src/layouts/`，頁面區塊與共用元件分開。AI 可以幫忙提出架構，但你仍要確認它是否適合自己日後維護。

## 怎麼把需求交給 AI，才看得出哪裡要改？

**先把頁面拆成可以單獨檢查的區塊，給每個區塊明確規格。** 當時我會說明元件名稱、需要接收的資料、預期畫面，以及應使用的 CSS 變數。比起只說「幫我做完首頁」，這樣更容易對照需求找出缺漏。

SEO 也是一樣。我讓 AI 協助處理 meta tags、社群預覽、結構化資料、RSS、sitemap 和文章路由，但網站要寫給誰、內容該回答甚麼問題，仍需要我決定。功能建好後，還要用實際頁面與檢查工具確認輸出，不能只看 AI 的完成訊息。

## 大範圍改版，甚麼適合交給 AI？

**當改動範圍大、規則又一致時，AI 特別適合做重複修改。** 當時我把原本的深色遊戲風格改成淺色，涉及 4 個全域 CSS 檔案與 7 個元件的樣式，並移除金色、發光與漸層效果。

原紀錄估計手動修改約需半天，AI 約十分鐘完成；這是當時的個人估計，不是不同專案都能達到的速度。那次的判斷重點是我先決定要改成甚麼樣，AI 再依規格處理多處相同的修改。完成後仍要看頁面，確認沒有因共用樣式改動而影響其他區塊。

## AI 給了結果，怎麼知道能不能交付？

**用你原本的需求逐項驗證，尤其是畫面、內容與連結。** AI 能協助找建置錯誤和 CSS 衝突，但它也可能加入不需要的功能，或在長對話中漏掉先前的限制。看到頁面能開只是起點；文章是否能找到、預覽資訊是否正確、手機上能否閱讀，都值得按專案需求實際檢查。

測試通過也要看它到底檢查了甚麼。我在[另一篇文章](/articles/ai-tests-false-safety-six-phase-overhaul/)拆過為甚麼全綠仍可能漏掉重要的問題。

下次讓 AI 做網站，先寫下三件事：這個網站要給誰用？這一輪完成後該看到甚麼？你要怎麼確認結果符合需求？
